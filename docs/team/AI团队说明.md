# AI 团队说明

这篇写给管理员，讲 AI 团队有哪些角色、一张需求单怎么从提出走到上线、AI 代审的规则、哪些事必须你亲自做，以及在审批 App 里怎么看看板和办公室。团队成员自己的详细工作规范在 `team/README.md`。

---

## 一、团队做什么

AI 团队每天自动迭代「知识图谱」（网页 + 安卓平板 App），用户是准备福建中考的学生。团队还维护管理员用的「团队审批」App 和腾讯云上的同步节点。
看板是私有仓库 **Walker-007-newland/knowledge-map-team** 的 Issue：一张 Issue = 一个需求单，状态用「状态:xxx」标签表示。

## 二、角色

| 角色 | 办公室工位 | 做什么 |
|---|---|---|
| 需求员 | 小需 | 每天体验产品、查内容质量和考纲变化，把问题和机会写成需求单（每天最多 2 个，先查重） |
| 产品 | 小品 | 评审需求：不做就否决；做就写「产品方案」（用户故事、具体改动、可逐条测试的验收标准、工作量、风险）；按审批意见修改方案 |
| 开发 / 开发2 / 开发3 | 小开 / 小发 / 小码 | 实现已批准的方案或修返工，每张单在独立的 git 工作区里做，写「开发说明」后提测；并行时每人一个工位 |
| 测试 | 小测 | 按验收标准逐条测试，写「测试报告」；通过就运行上线脚本发布并评论「已上线」，不通过退回返工 |
| 文员 | 小文 | 维护 `docs/` 下全部文档：使用手册、更新说明、运维手册、本说明；每次上线后更新，每天早上巡查（2026-10-19 加入） |
| CEO | CEO 室 | 调度员兼 AI 审批员：安排各角色工作、按代审规则审批方案 |
| 管理员（你） | — | 随时可推翻 AI 审批；处理「阻塞」；做需要真人的事（见第五节） |

## 三、一张需求单的流程

```
需求员提出 → 待评审 → 产品出方案 → 待审批 → (AI 代审 / 你) → 已批准 → 开发中 → 待测试 → 测试通过 → 已上线（关闭）
                │                         │    ↑                                        │
                ↓                         │    └── 需修改（产品改方案）                   └→ 返工（开发修）
            产品否决（关闭）               └→ 已驳回（产品关闭）
任何一步卡住需要人 → 阻塞（评论写清原因，等你处理）
```

| 状态 | 谁处理 | 下一步 |
|---|---|---|
| 待评审 | 产品 | 否决（关闭）或写方案 → 待审批 |
| 待审批 | AI 代审 / 你 | 批准 / 要求修改 / 驳回 / 转阻塞 |
| 需修改 | 产品 | 发「产品方案 v2」→ 待审批 |
| 已驳回 | 产品 | 关闭 |
| 已批准 | 开发 | 开发中 → 待测试 |
| 返工 | 开发 | 修复 → 待测试 |
| 待测试 | 测试 | 通过：上线并关闭（分期的单改回「已批准」做下一期）；不通过：返工 |
| 阻塞 | 你 | 在审批 App 里交回开发 / 交回测试 / 让产品改方案 / 驳回 |

- 同一张单**返工满 3 次**仍不通过，测试会改为「阻塞」等你决定。
- **依赖**：方案写了「依赖 #m」而 #m 还没上线，开发先跳过这张单。
- **分期**：大单分几期做，每期单独测试上线，评论「已上线（第 N 期）」，最后一期才关单。

### 真机测试（两台 USB 设备）
需要在真平板上验收的单（比如 #1 设备同步），由**测试员用电脑 USB 连着的两台安卓设备**来做，不用你动手（#1 第一期就是这样验收的）：
- 两台设备：新大陆 P70（Android 14，横屏，能截图）、新大陆 X800（Android 12，竖屏；支付终端，系统禁止截图录屏，测试员改为读屏幕文字核对）。两台都没有 SIM 卡，只能连同一个 Wi-Fi。
- 做法：先装线上正式版、导入测试数据，再覆盖安装测试包，确认升级不丢数据，然后按方案里的真机验收步骤逐条操作，结果写进「测试报告」。
- 需要邀请码时，测试员现生成一张临时测试邀请码，测完作废，并删掉测试用的同步组；不动初始邀请码。
- 测完把两台设备装回新的正式版（不留学习数据），删掉推上去的测试文件和备份；不改系统设置、别的 App 和账号。
- 做不了的步骤会在报告里写明并跳过，比如「把小狗放到桌面」要在系统设置里开权限，测试员不改设备设置，所以没测。
- 每个角色的评论第一行是固定标题（「## 产品方案」「## 开发说明」「## 测试报告」「## 已上线」等），审批 App 靠它识别。

### 定时运行
| 任务 | 时间 | 内容 |
|---|---|---|
| AI 团队·每日需求与方案 | 每天 9:00 | 需求员提需求、产品出方案、调度员代审、文员巡查文档 |
| AI 团队·开发测试上线 | 每天 10:00–22:00 每 2 小时 | 产品改方案并代审，开发 → 测试 → 通过即上线（遵守依赖与分期） |

### 上线方式
| 改了什么 | 上线脚本 | 结果 |
|---|---|---|
| 知识图谱 App | `team/release.ps1` | 打包 APK，发 GitHub Release + 国内镜像，学生平板打开 App 时提示更新 |
| 审批 App / 同步节点 | `team/release-admin.ps1` | 部署节点 + 发布审批 App（你的手机打开 App 时提示更新） |
| 文档 | `team/docs-commit.ps1` | 只提交 `docs/` |

三个脚本共用一把排队锁，同一时间只上线一个。上线用工作区里已提交的代码，你在主目录 `teach/` 里没提交的改动不会被带进正式版；但如果你的未提交改动和本次上线改了同一个文件，上线会停下（退出码 3）并转阻塞。

## 四、AI 代审规则（2026-10-16 起）

你已把审批交给 AI。调度员在产品出方案后逐个审，评论正文首行写「（AI 代审）」并说明理由。**你随时可以在审批 App 里推翻**。

- **批准**：对中考备考有价值、范围清楚、验收标准逐条可测、不破坏学生已有数据（改数据结构必须有迁移和备份）。
- **要求修改**：验收标准不可测、漏了迁移 / 回滚、范围过大应分期等。同一单最多退回 2 次，第 3 次仍不行就转阻塞。
- **驳回**：价值低、和现有功能重复、或超出产品定位。
- **必须转阻塞等你**：要花钱或续费；注册 / 实名外部账号；提供密钥或密码；在云控制台开端口、改配置；收集学生个人信息；删除或不可逆地改学生数据。
- 审批结论会写进调度员的汇报，每条审批评论你都能在 App 里看到。

## 六、在审批 App 里看团队

- **待审批**标签：等你（或 AI 代审）处理的方案和阻塞单。**进行中**：已批准、开发中、待测试、返工、需修改。**待评审**：刚提的需求。**已结束**：已关闭的单。
- 点开一张单能看到需求正文和全部评论：产品方案、审批意见、开发说明、测试报告、已上线（含版本号和下载地址）。
- **办公室**：每个成员上报自己的状态——打字 = 工作中，喝咖啡 = 空闲，头顶红色感叹号 = 阻塞；旁边写着在做什么。工作中超过 3 小时没更新显示「可能已中断」。下方「最近动态」是最近的状态变化。这些状态存在看板里带「团队状态」标签的那张单上，由团队成员自动更新，请勿手动编辑或关闭（看板列表会自动排除它）。
- 后台每约 30 分钟检查一次，有新的待审批 / 阻塞单会发通知。
- 详细操作见《[审批 App 使用手册](../team-admin-app/使用手册.md)》。
